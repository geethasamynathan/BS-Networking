STEP 01

What we are building and what you will learn

Goal: build a small CompanyABC e-commerce web-tier demo on Azure: a customer-facing public Load Balancer, two Ubuntu web VMs managed by a Flexible VM Scale Set, automatic installation of NGINX, and CPU-based scale-out/scale-in.

This example begins with two VMs and permits scaling between two and five. The page displays each machine's hostname, so the instructor can explain which VM handled a request. This is a web-tier training simulation, not a complete checkout/payment system.

Terminology: AWS VPC = Azure Virtual Network (VNet); AWS Security Group ≈ Azure Network Security Group (NSG); AWS target group ≈ Azure Load Balancer backend pool. The Azure frontend is called Frontend IP configuration, not a frontend pool.

Learning sequence

  1. Create the resource group, VNet, subnet and NSG.
  2. Create the public IP and Standard public Load Balancer.
  3. Set up backend pool, health probe, load-balancing rule and inbound NAT choices.
  4. Set up outbound internet access (and explain why NAT Gateway is optional, not an inbound requirement).
  5. Create the Flexible VMSS with two Ubuntu VMs and attach its backend to the Load Balancer.
  6. Install the same web application on every existing and future VM.
  7. Verify NSGs at both subnet and NIC scope, health, backend membership and browser access.
  8. Configure scaling rules, including the hidden Add a rule link seen in the earlier Portal.
  9. Apply lessons from the actual CompanyABC-VMSS2 troubleshooting session.

Create resource group

  1. Open portal.azure.com → search Resource groups → Create.

  3. Select Review + create → Create.
  4. Do not reuse a resource group containing other class labs if you plan to delete everything afterward.
STEP 04

Create VNet and subnet

  1. Search Virtual networks → Create.
  2. Basics: choose RG-VMSS-Lab, name CompanyABC-VNet, region Central India.
  3. On the Security page leave optional Firewall/Bastion disabled for this first lab.
  4. Go to IP addresses; enter VNet address space 10.10.0.0/16.
  5. If the wizard created a default subnet, edit or remove it. Add Web-Subnet with CIDR 10.10.1.0/24.
  6. For private subnet / default outbound access, prefer private without default outbound where offered; later provide an explicit outbound method.
  7. Review → Create; then inspect VNet → Subnets and confirm the exact name/CIDR.
A /24 subnet contains 256 addresses, of which Azure reserves five. You do not create one subnet per VM.
STEP 05

Create NSG and associate it with Web-Subnet

  1. Search Network security groups → Create. Name CompanyABC-Web-NSG, Central India, in RG-VMSS-Lab.
  2. Open it → Inbound security rules → Add.
  3. Set Source Service Tag → Internet, Source port *, Destination Any, Protocol TCP, Destination port 80, Action Allow, Priority 300, Name Allow-HTTP-80.
  4. Save rule. Keep default AllowAzureLoadBalancerInBound rule (65001) for Azure health probe traffic.
  5. NSG → Subnets → Associate → choose CompanyABC-VNet and Web-Subnet.
  6. Open the subnet itself and verify that CompanyABC-Web-NSG appears.

Lesson from your other chat: an NSG attached to a VM network interface also applies. The traffic must be permitted by both subnet- and NIC-level NSGs if both exist. A NIC-level basic NSG can therefore block HTTP even when the subnet NSG permits it.
STEP 06

Create the Standard public Load Balancer

  1. Search Load balancers → Create → Standard Load Balancer.
  2. Basics: subscription; RG-VMSS-Lab; name CompanyABC-Web-LB; region Central India.
  3. SKU Standard; Type Public; Tier Regional.
  4. Go to Frontend IP configuration (next tab).
The Load Balancer is the customer inbound endpoint. NAT Gateway is not the website entrance and is not needed for the load balancer to receive connections.
STEP 07

Create LB public IP and frontend configuration

  1. On Frontend IP configuration, select + Add a frontend IP configuration.
  2. Name CompanyABC-Frontend; IP version IPv4; choose Public IP address → Create new.
  3. Create IP resource named CompanyABC-Web-PIP; SKU Standard, allocation Static; zone redundancy only if offered/compatible.
  4. Under Routing preference, choose Microsoft network for this example (where shown).
  5. Save public IP dialog; then Save/Add frontend configuration. Verify frontend CompanyABC-Frontend is attached to CompanyABC-Web-PIP.
Never enter your home IP address here. Azure assigns the Load Balancer public IPv4. Your office public IP is only relevant for restricted SSH/RDP access.
STEP 08

Create the backend pool

  1. Open the Backend pools tab → + Add a backend pool.
  2. Name: CompanyABC-BackendPool; choose CompanyABC-VNet when requested.
  3. Choose a backend association mode compatible with the creation wizard. An IP-address-based pool is common in the Standard LB quickstart; NIC-based membership is also supported.
  4. Because the VMs do not yet exist, save an empty pool. Do not invent individual private IPs.
  5. When creating the VMSS, explicitly select this existing backend pool; later verify all actual instances are associated.
A backend pool is not a target-group URL. You browse the frontend public IP, not the backend pool name.
STEP 09

Create HTTP health probe

  1. In Inbound rules → Health probes or Load Balancer → Health probes, select Add.
  2. Name CompanyABC-HTTP-Probe.
  3. Protocol HTTP; port 80; path /; interval 5 seconds where selectable; unhealthy threshold 2.
  4. Save. The NGINX home page must return HTTP success for GET /.
  5. Do not use HTTPS probe unless HTTPS is configured on the VM itself.
Backend health is independent of whether the customer can see the webpage. A VM may have NGINX working locally but still be unhealthy due to NSG, wrong probe path, or network rules.
STEP 10

Create the inbound load-balancing rule

  1. Within LB creation wizard or after creation, open Load-balancing rules → Add.
  2. Name CompanyABC-HTTP-Rule.
  3. Frontend CompanyABC-Frontend and backend CompanyABC-BackendPool.
  4. Protocol TCP; frontend Port 80; backend Port 80; HA Ports Off.
  5. Health probe CompanyABC-HTTP-Probe.
  6. Session persistence None; TCP reset On if supported; Floating IP Off; idle timeout default or 15 minutes.
  7. For outbound SNAT, use an explicit outbound setup. Where the rule asks about implicit outbound SNAT, do not depend on implicit SNAT; this tutorial describes NAT Gateway as a choice.
  8. Save the rule, then complete Review + create → Create for the Load Balancer.

STEP 11

NAT Gateway explained clearly: why, when, and whether required

Answer to your question: Why do we want NAT Public IP? We need an outbound path only if a VM must initiate connections to internet destinations such as Ubuntu package repositories, external APIs or update servers. A NAT Gateway can provide that outbound path from private instances. The NAT public IP is the source address internet services see, not the public address customers visit.

ScenarioNAT Gateway needed?Why
Customers browse website via LB public IPNoLB frontend handles incoming web traffic
Private Ubuntu VM downloads NGINX packagesYes, or another explicit outbound methodVM needs internet access
VM image already contains all app packages and no outbound callsPossibly noNo general internet egress required
VM has public IP and public egress worksNot necessarilyInstance-level IP can provide outbound, though not preferred for private production web tier
Use Standard LB explicit outbound SNAT ruleNo separate NAT Gateway requiredOutbound alternative with SNAT planning
Production controlled predictable outbound IPOften recommendedSimplifies allowlisting external services
Do not confuse these: CompanyABC-Web-PIP = inbound customers → Load Balancer. CompanyABC-NAT-PIP = VM initiated outbound traffic → Internet. They are distinct IP resources. NAT Gateway never takes customer HTTP traffic and forwards it to the web server.

For this reproducible lab, we use a NAT Gateway because the automated Ubuntu initialization installs NGINX from the internet. You may omit NAT if you instead use another correctly configured outbound method or a pre-baked image that needs no internet egress.

STEP 16

Automatically deploy NGINX on every instance

NGINX is not installed merely by creating an Ubuntu VM. Your first two VMs and each newly added VM must get the same application.

Example cloud-init for an Ubuntu-based VMSS

#cloud-config
package_update: true
packages:
  - nginx
write_files:
  - path: /var/www/html/index.html
    permissions: '0644'
    content: |
      <!doctype html>
      <html lang="en">
      <head><meta charset="utf-8"><title>CompanyABC Shopping</title>
      <style>body{font:18px Arial;padding:30px;background:#f3f7ff}
      main{background:white;border-radius:12px;padding:24px;max-width:680px}</style>
      </head>
      <body><main><h1>CompanyABC Shopping</h1>
      <p>Azure VM Scale Set e-commerce demo.</p>
      <p>Served by <strong>__HOSTNAME__</strong></p>
      </main></body></html>
runcmd:
  - sed -i "s/__HOSTNAME__/$(hostname)/g" /var/www/html/index.html
  - systemctl enable nginx
  - systemctl restart nginx
  1. Where the creation wizard exposes supported Custom data / cloud-init for the VMSS scaling profile, paste this configuration there.
  2. If the Portal does not expose VMSS-model custom data, configure a VMSS-supported Custom Script Extension, VM Applications, or a prepared Azure Compute Gallery image instead.
  3. If using a script extension, place the script in an accessible trusted location and configure it on the Scale Set model, not just on VM 1.
  4. The page contains a __HOSTNAME__ placeholder that cloud-init replaces with each VM’s hostname.
  5. For a live class, verify a new third instance has the page before claiming autoscale is application-ready.
Do not put this cloud-init YAML into a Windows Server VM. Use IIS plus a Windows-compatible script/extension or custom Windows image instead.

STEP 17

Create, verify instances and backend registration

  1. Select Review + create → Create. Download any SSH private key securely if prompted.
  2. Open Virtual machine scale sets → CompanyABC-VMSS → Instances; expect two instances if both allocations succeeded.
  3. Open Load balancers → CompanyABC-Web-LB → Backend pools → CompanyABC-BackendPool. Verify actual instance NICs/private IP addresses are associated.
  4. Open Health probes / Backend health if offered; expect HTTP probe healthy after NGINX initialization.
  5. Open Frontend IP configuration and copy the Load Balancer public IPv4 address. Browse http://YOUR-LB-PUBLIC-IP.
  6. Refresh a few times. It may show different hostnames, but load balancing is per flow and is not guaranteed to alternate every refresh.
An empty backend pool means the VMSS network interface or IP configuration is not correctly associated. A healthy individual VM does not prove the public Load Balancer rule works.
STEP 18

How an e-commerce request actually reaches the servers

  1. Customer opens http://YOUR-LB-PUBLIC-IP/.
  2. Inbound request reaches the Azure Load Balancer frontend CompanyABC-Frontend on port 80.
  3. Rule CompanyABC-HTTP-Rule sends TCP :80 to eligible healthy members in CompanyABC-BackendPool.
  4. Traffic must pass effective subnet and NIC NSGs, and NGINX must listen on port 80.
  5. VM returns the HTTP response to the same customer connection.
  6. Azure Monitor observes metrics separately and can change the number of members over time.

Production e-commerce: replace direct plain HTTP entry with HTTPS/TLS termination and WAF protection (for example, Azure Application Gateway). Keep products/orders in shared data services, not on local VM disks.

STEP 19

Autoscale: instance limits and default profile

  1. Open VM Scale Sets → CompanyABC-VMSS → Scaling.
  2. Select Custom autoscale / Scale based on a metric, depending on your Portal version.
  3. If you see named Default and Profile 1 profiles, keep the active Default metric-based profile; remove an accidental unused extra Profile 1 only after checking it is not needed.
  4. Set Minimum = 2, Maximum = 5, Default = 2.
  5. Find Default → Rules. Sometimes Add a rule appears as a small blue text link inside a yellow warning, not a large button. Select that link.
  6. If no add link appears, confirm you are editing the correct autoscale profile, have selected metric-based rather than fixed instance count, and have appropriate write permissions.

STEP 21

Test manual scaling, then automatic scaling

  1. First test: temporarily switch to Manual, increase count from 2 to 3, Save, and verify the third VM appears in Instances.
  2. Verify third VM received website setup, is in the backend pool and is healthy. If not, fix your image/extension before autoscale.
  3. Restore Custom autoscale; check the min/max and both rules were saved.
  4. For automatic scaling, run a controlled authorized CPU load on the lab servers. Watch Percentage CPU and autoscale Run history.
  5. Stop the test workload, allow the monitored average CPU to fall, and observe scale-in events when conditions permit.
  6. Never run stress tests against unrelated public websites or uncontrolled shared machines.
Scale-out = horizontal scaling, for example 2 → 3 VMs. Scale-in = 3 → 2 VMs. Scale-up is resizing each VM, which is not performed by these CPU autoscale rules.

What happened and what resolved the confusion

  2. We checked backend pool registration, HTTP probe / on port 80, and frontend TCP 80 → backend TCP 80 rule.
