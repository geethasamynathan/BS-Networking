AWS Application Load Balancer
Mumbai Region — From Scratch

Build one custom VPC, two public subnets in two Mumbai Availability Zones, two Windows EC2 IIS web servers, a target group, and an internet-facing Application Load Balancer. Every choice is explained with a real use case and exact Console steps.

1. Practical goal and architecture

CompanyABC runs a shopping website. When only one server serves customers, a failure can interrupt the entire site. With an Application Load Balancer (ALB), the same website address sends requests to healthy registered EC2 servers.

Region vs AZ: Both ap-south-1a and ap-south-1b are inside the same Mumbai Region (ap-south-1). Choose two different AZs that your account permits. The exact AZ-letter mapping may vary by account.

2. Explain every AWS term before the lab

VPC

Your private virtual network in AWS. It owns the primary IP range for this lab.

Subnet

A smaller IP range within one Availability Zone; servers and ALB network interfaces use it.

Application Load Balancer

A managed Layer 7 entry point for HTTP/HTTPS that routes requests to registered healthy backends.

Elastic Load Balancing (ELB) versus Application Load Balancer (ALB)
ELB is the family of AWS managed load balancing services. ALB is the HTTP/HTTPS-focused type used in this lab. Other types include NLB (network protocols/performance) and GWLB (network appliances). ALB can route by URL path or hostname.
Region versus Availability Zone (AZ)
A Region is a geographic AWS location such as Mumbai. An AZ is an independently operated infrastructure location within the Region. An ALB requires subnet mappings in at least two AZs for a standard deployment.
CIDR
Classless Inter-Domain Routing. 10.0.0.0/16 is the larger VPC private-address space; 10.0.1.0/24 and 10.0.2.0/24 are nonoverlapping smaller subnets. A /24 has 256 addresses, five of which AWS reserves, leaving 251 for use by resources.
Public versus private subnet
A subnet is called public when its effective route table has a route to the VPC Internet Gateway. An EC2 instance also needs a public IP address and permitted firewall rules to be reachable directly from the internet. A private subnet does not have a direct route to the Internet Gateway.
Internet Gateway (IGW)
A VPC attachment supporting internet connectivity. It is not a firewall or a load balancer; route tables and security rules must also be configured.
Route Table
Network forwarding instructions. 10.0.0.0/16 → local connects resources inside the VPC. 0.0.0.0/0 → IGW is the IPv4 internet default route for a public subnet.
Security Group (SG)
A stateful virtual firewall attached to resources. We use Mumbai-ALB-SG to allow browser HTTP, and Mumbai-Web-SG to allow backend HTTP from the ALB SG and RDP from the trainer's current IP.
Network ACL
A stateless subnet-level network filter. Keep the automatically created default NACL in this lab unless your organization has restricted it. Custom NACLs may need outbound ephemeral-port responses allowed.
EC2, AMI and IIS
EC2 is AWS virtual computing. An AMI is a machine image used when launching an instance. IIS is Microsoft's web server that serves our HTML pages on Windows Server.
Listener
A front-end protocol/port combination on the ALB. Our HTTP:80 listener forwards client requests to Mumbai-TG. In production, HTTPS:443 is normally preferred.
Target Group (TG)
A logical set of backend destinations registered by instance ID, IP, or another supported type. This lab registers two EC2 instances by instance ID and forwards to their HTTP port 80.
Health Check
Periodic ALB request to the configured HTTP path, here /index.html. A healthy HTTP 200 response makes a registered instance eligible to receive requests. Health checks show reachability and basic web response, not complete application correctness.
DNS name
The AWS-provided hostname of the ALB. Customers visit one address, even as the selected backend changes. This hostname is not a fixed IP address.
Cross-zone and round-robin
ALB can distribute requests across registered healthy targets in its enabled AZs. Default target-selection algorithm is round robin, but browser refreshes do not guarantee a perfect A/B/A/B sequence.
Auto Scaling
Separate AWS feature that can launch/replace EC2 instances in response to policies. A load balancer alone does not create replacement EC2 instances.
Why two AZs, not two Regions? We want zone-level redundancy within Mumbai; this does not require permission for any second Region. The lab can use ap-south-1a and ap-south-1b, or any other two permitted standard AZs in Mumbai.

5. Create the Internet Gateway and public routes

STEP 4 — Create and attach Internet GatewayExpand / collapse
  1. Open VPC → Internet Gateways → Create internet gateway.
  2. Name: Mumbai-LB-IGW. Choose Create internet gateway.
  3. Select the new Internet Gateway. Choose Actions → Attach to VPC.
  4. Choose Mumbai-LB-VPC → Attach internet gateway.
  5. Confirm the state is Attached.
Why this matters

The IGW lets public subnets communicate with the internet. Creating it alone is not enough; the route table must point to it.

STEP 5 — Create a public route table and add routesExpand / collapse
  1. Open VPC → Route Tables → Create route table.
  2. Name: Mumbai-Public-RT. VPC: Mumbai-LB-VPC. Click Create.
  3. Select the route table → Routes → Edit routes → Add route.
  4. Destination: 0.0.0.0/0; Target: Internet Gateway → Mumbai-LB-IGW.
  5. Keep the existing local VPC route and choose Save changes.
DestinationTargetWhy
10.0.0.0/16localIntra-VPC communication
0.0.0.0/0Mumbai-LB-IGWDefault route to internet
Why this matters

This tells the VPC how to forward internet-bound IPv4 packets.

STEP 6 — Explicitly associate BOTH subnetsExpand / collapse
  1. On Mumbai-Public-RT, open Subnet associations.
  2. Choose Edit subnet associations.
  3. Check Mumbai-Public-Subnet-A and Mumbai-Public-Subnet-B.
  4. Choose Save associations.
  5. Confirm both appear under Explicit subnet associations.
Common mistake: Creating a route table is not enough. Without explicitly associating the two subnets, they may still use the main route table, which lacks your internet route.
Why this matters

These associations make both chosen subnets public through their IGW default route.

STEP 7 — Enable public IPv4 for RDP trainingExpand / collapse
  1. Go to VPC → Subnets, select Mumbai-Public-Subnet-A.
  2. Choose Actions → Edit subnet settings.
  3. Enable Auto-assign public IPv4 address → Save.
  4. Repeat for Mumbai-Public-Subnet-B.
  5. Later, when launching each instance, explicitly confirm Auto-assign public IP: Enable.
A subnet route makes a subnet public; a public IPv4 address is a separate property of an EC2 instance. For this lab both are required for direct laptop RDP.
Why this matters

The trainer can connect to Windows using RDP. Production web servers typically reside in private subnets and are administered by a safer private method.

6. Security Groups — what every rule means

Use two security groups: one protecting the internet-facing ALB and one protecting the Windows EC2 backend. AWS Security Groups are stateful, so response packets for permitted connections are tracked automatically.

STEP 8 — Create Mumbai-ALB-SGExpand / collapse
  1. Open EC2 → Network & Security → Security Groups → Create security group.
  2. Name: Mumbai-ALB-SG. Description: Allow public HTTP to Mumbai ALB.
  3. Select VPC: Mumbai-LB-VPC.
  4. Under Inbound rules, choose Add rule: Type HTTP; Port 80; Source Anywhere-IPv4 (0.0.0.0/0).
  5. For the introductory lab, retain the default outbound allow-all rule. Click Create security group.
TypePortSourceMeaning
HTTP800.0.0.0/0Client browsers can access ALB
Why this matters

The ALB is a public HTTP entry point, so its listener port must be reachable.

STEP 9 — Create Mumbai-Web-SGExpand / collapse
  1. Create another Security Group in the same VPC.
  2. Name: Mumbai-Web-SG. Description: Backend IIS and restricted RDP.
  3. Inbound rule 1: RDP, port 3389, source My IP.
  4. Inbound rule 2: HTTP, port 80, source type Custom, select security group Mumbai-ALB-SG (its SG ID).
  5. Retain default outbound allow-all for this classroom exercise and click Create security group.
TypePortSourceMeaning
RDP3389My IPWindows GUI admin from current public IP
HTTP80Mumbai-ALB-SGOnly ALB-associated traffic can reach IIS
Do not open RDP globally: Never set RDP 3389 to 0.0.0.0/0 just to make the demo work. The instructor/participant may need to update “My IP” if their public address changes.
Why this matters

This separates the internet-facing front end from the EC2 back end. It reduces direct exposure of port 80 on the web servers.

9. Target Group, health checks, ALB and listener

Understand the relationship: Customer → ALB listener HTTP:80 → routing rule → Mumbai-TG → one healthy EC2 target at HTTP:80. The ALB terminates the client connection and makes a backend connection; it does not simply redirect the browser to an EC2 public IP.

STEP 14 — Create Mumbai-TG and register EC2 targetsExpand / collapse
  1. In EC2, scroll left navigation to Load Balancing → Target Groups → Create target group.
  2. Target type: Instances. Target Group name: Mumbai-TG. Protocol: HTTP. Port: 80. IP address type: IPv4.
  3. VPC: Mumbai-LB-VPC. Protocol version: HTTP1.
  4. Under Health checks: Protocol HTTP; Path /index.html; Port Traffic port; Success codes 200. Leave other health check values as defaults.
  5. Choose Next. Select Mumbai-Web-A and Mumbai-Web-B. Port 80 for both.
  6. Choose Include as pending below, confirm both pending targets, and choose Create target group.

Why this matters

Health checks ensure the ALB generally selects only healthy targets. A newly created TG may show Initial or Unused before the associated ALB/listener is ready.

STEP 15 — Create the internet-facing ALBExpand / collapse
  1. Go to EC2 → Load Balancing → Load Balancers → Create load balancer.
  2. Choose Application Load Balancer → Create.
  3. Name: Mumbai-ALB; Scheme: Internet-facing; IP address type: IPv4.
  4. Under Network mapping, select Mumbai-LB-VPC.
  5. Enable ap-south-1a and choose Mumbai-Public-Subnet-A. Enable ap-south-1b and choose Mumbai-Public-Subnet-B.
  6. Under Security groups, choose Mumbai-ALB-SG; remove an unnecessary default SG if selected.
  7. Under Listeners and routing, Protocol HTTP, Port 80, Default action Forward to target group → Mumbai-TG.
  8. Review and choose Create load balancer. Check load balancer state becomes Active.

The ALB becomes one stable DNS endpoint to route client requests. Its node addresses may change; use its DNS name.

10. Demonstrate working load balancing and failover

STEP 16 — Check targets are healthyExpand / collapse
  1. Open EC2 → Target Groups → Mumbai-TG → Targets.
  2. Look for both rows: Mumbai-Web-A, HTTP:80, Healthy and Mumbai-Web-B, HTTP:80, Healthy.
  3. If they are Initial, permit health checks to complete. If Unused, verify the ALB listener uses this Target Group and the targets’ AZs are enabled.
  4. If Unhealthy, test http://localhost/index.html on each Windows server and check security group and Windows Firewall.
Why this matters

Healthy means ALB can reach the configured HTTP check page on that target.

STEP 17 — Access the ALB DNS and identify which server respondsExpand / collapse
  1. Go to EC2 → Load Balancers → Mumbai-ALB → Details.
  2. Copy the DNS name shown by AWS. The displayed hostname is generated and differs by account.
  3. Open a local browser tab and enter http://YOUR-ALB-DNS-NAME/index.html (HTTP, not HTTPS).
  4. Observe the blue Server A page or the green Server B page.
  5. Refresh multiple times or use fresh requests; eventually verify both servers can handle requests. For browser testing, use developer tools with cache disabled if needed.
Example format only: Mumbai-ALB-123456789.ap-south-1.elb.amazonaws.com. This is not a working address. Copy your actual DNS name from the Console.
Why this matters

Both pages are accessible through one ALB hostname. Target selection may not perfectly alternate on every refresh.

STEP 18 — Stop IIS on Server A, observe failover, restartExpand / collapse
  1. RDP into Mumbai-Web-A. Open Internet Information Services (IIS) Manager.
  2. Expand Sites, select Default Web Site, then click Stop in the Actions pane.
  3. Go to EC2 → Target Groups → Mumbai-TG → Targets. After failed health checks reach the configured threshold, Server A should show Unhealthy.
  4. Verify Mumbai-Web-B remains Healthy. Open the ALB DNS /index.html again. Requests should now be served by Server B.
  5. Return to IIS Manager on Server A and choose Start. Check the local page, then wait for healthy checks to re-register it as eligible.
Why this matters

This tests application-level failover. Stopping IIS does not terminate the EC2 instance. If all targets are unhealthy, ALB may fail open and still route to unhealthy targets.

12. Cost, security and cleanup

Running two Windows EC2 instances and an ALB costs money even when your students are not browsing. Additional charges can apply to ALB capacity usage, EBS storage, public IPv4 addresses, traffic and monitoring. Rates vary by account and Region; review AWS Pricing/Billing rather than assuming a fixed lab cost.

Safe cleanup order: Delete Mumbai-ALB → delete Mumbai-TG → terminate the two lab-only EC2 instances → delete lab Security Groups → remove route table associations and delete lab route table → detach and delete lab IGW → delete the lab subnets → delete the custom lab VPC. Verify resource dependencies and any remaining volumes or public IPv4 allocations. Never delete existing/shared resources.

Production improvements (after the classroom lab)

  • HTTPS 443 listener and an AWS Certificate Manager certificate for a real domain.
  • EC2 backends in private subnets, avoiding public RDP exposure.
  • Auto Scaling Group to maintain and replace required backend capacity.
  • CloudWatch alarms for unhealthy targets, request volume and 5xx responses.
  • Review ALB access logs, AWS WAF, least-privilege IAM and cost budgets as needed.

13. Recap questions with answers

Q1. Can two EC2 instances in the same Region be load balanced?Expand / collapse
Yes. Both servers can be in ap-south-1, preferably in different AZs to improve resilience.
Q2. Why create two subnets?Expand / collapse
Each subnet is tied to one AZ. A normal ALB requires two enabled AZ subnet mappings; our two public subnets provide them.
Q3. Why is the VPC range /16 while each subnet is /24?Expand / collapse
A VPC defines the larger available address pool. Each /24 is a distinct nonoverlapping part of that pool with 256 total IPv4 addresses.
Q4. What makes a subnet public?Expand / collapse
Its effective route table must contain a default route to an attached Internet Gateway. A public IP on EC2 is separately needed for direct IPv4 internet connectivity.
Q5. Why use two Security Groups?Expand / collapse
The ALB SG allows customer HTTP traffic; the EC2 SG allows backend HTTP only from the ALB SG and restricted RDP from a known administrator IP.
Q6. What is the difference between an ALB, listener and Target Group?Expand / collapse
ALB is the traffic entry point; listener defines HTTP:80 routing; Target Group contains the backend registered instances.
Q7. What does a health check do?Expand / collapse
It requests /index.html on each target and checks for the expected HTTP response, such as status 200.
Q8. What happens when Server A IIS stops?Expand / collapse
If Server B is healthy, the ALB normally stops routing to unhealthy Server A and continues using Server B after detecting the failure.
Q9. Does ALB create new EC2 servers automatically?Expand / collapse
No. It routes requests. Use EC2 Auto Scaling separately to launch/replace instances automatically.
Q10. What does the browser use to reach the ALB?Expand / collapse
The AWS-provided ALB DNS hostname. Use HTTP for this lab; a production site should normally use HTTPS.
