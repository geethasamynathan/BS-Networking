AWS Target Groups — Concept to Hands-on

Understand what a Target Group does, why ALB needs it, what each setting means, and exactly how to register Mumbai-Web-A and Mumbai-Web-B using the AWS Console.

1. What is a Target Group?

A Target Group is a logical collection of destinations (called targets) that a Load Balancer can send requests to. In our demo the targets are two EC2 instances running IIS.

  • Application Load Balancer (ALB): Accepts customer traffic and selects a suitable backend target.
  • Target Group (Mumbai-TG): Defines the backend servers, their protocol/port, and health-check configuration.
  • EC2 Web Servers: Run the application and return HTML responses.

Real use case: CompanyABC's online shopping site has many customers. Instead of relying on one Windows web server, the ALB distributes requests across two healthy servers, increasing availability.

2. Architecture — the request flow

Logical illustration; actual health depends on your AWS resources.

Request flow: Browser → ALB HTTP listener → forwarding rule → Mumbai-TG → selected healthy EC2 instance → HTML response. The target group does not function as an independent public load balancer.

3. What happens if Server A fails?

ALB periodically tests the target group's registered targets. Once Server A fails the required health checks, ALB normally stops selecting it while Server B remains healthy. When Server A recovers and passes its recovery checks, it becomes eligible again.

Training note: Real AWS failover is not immediate. Health checks need time to detect failures. If every registered target is unhealthy, ALB may fail open and route to unhealthy targets.

5. Health checks explained

The ALB periodically sends an HTTP request to each registered server at http://<private-EC2-IP>:80/index.html. A response matching the success-code setting indicates that the HTTP health check passed.

SettingValue in your screenExplanation
ProtocolHTTPUse an HTTP request to test IIS.
Path/index.htmlTest a real file created on both servers.
PortTraffic portChecks the same port used by the targets (80).
Healthy threshold5Five consecutive successes to recover from Unhealthy to Healthy.
Unhealthy threshold2Two consecutive failures to mark a healthy target Unhealthy.
Timeout5 secondsMaximum wait for an individual health-check response.
Interval30 secondsApproximate spacing between checks on a target.
Success codes200HTTP 200 indicates a successful page response.

Why test /index.html? Because the lab creates a page with that name. Using only / could test IIS's default document instead of the page that participants built.

Before creating the target group, verify http://localhost/index.html works on each Windows EC2 server, and that their EC2 security group permits HTTP port 80 from the ALB security group. Initial target registration can become healthy after one successful initial check; the configured healthy threshold applies to recovering targets.

6. Your AWS Console screenshots, annotated

7. Continue your lab — exact AWS Console actions

Step 1 — Click Next

After verifying all the settings in your screenshots, click Next at the bottom of the Target Group creation screen.

Step 2 — Register both Windows EC2 servers

  1. On Register targets, locate the available instances.
  2. Tick Mumbai-Web-A and Mumbai-Web-B (both must be in Mumbai-LB-VPC).
  3. Leave the target port at 80.
  4. Click Include as pending below.
  5. Confirm both appear in the pending-targets list.

Step 3 — Review and create

Choose Next, review the target group and registered instances, then click Create target group.

Step 4 — Create or configure the ALB

Navigate to EC2 → Load Balancers → Create load balancer → Application Load Balancer. Use the same VPC, two public subnets in different Mumbai Availability Zones, your ALB security group, and an HTTP:80 listener that forwards to Mumbai-TG.

Step 5 — Confirm targets are Healthy

Navigate to EC2 → Target Groups → Mumbai-TG → Targets. After the ALB listener is configured and health checks succeed, verify both instances show Healthy. An Unused status before a listener references the group can be normal.

Step 6 — Test load balancing and failover

  1. Find the ALB's actual DNS name in EC2 → Load Balancers → Details.
  2. Open http://YOUR-ALB-DNS-NAME/index.html.
  3. Repeat uncached requests and look for the two distinctive pages.
  4. For failure testing, stop Default Web Site in IIS Manager on Server A; verify it becomes Unhealthy and Server B continues responding.
  5. Restart IIS on A and verify it becomes Healthy again.

9. Recap questions with answers

Q1. Does a Target Group distribute requests by itself?
No. The ALB performs request routing using the selected target group and its target health information.
Q2. Why is target type Instances?
We are registering two EC2 instances by their instance IDs.
Q3. Why use port 80?
The IIS web applications accept HTTP requests on port 80.
Q4. Why have health checks?
They detect whether each registered server can respond successfully to the configured HTTP request.
Q5. What happens when IIS stops on Server A?
After the failure threshold, ALB normally routes new requests only to healthy Server B, as long as Server B remains available.
Q6. Does an ALB automatically launch replacement EC2 machines?
No. EC2 Auto Scaling is a separate service for launching and replacing instances.
Q7. Why use two Mumbai Availability Zones?
The two AZs improve resilience while keeping resources in the same Mumbai Region.

Instructor one-liner: The ALB is the traffic controller, the Target Group defines the backend servers and their health checks, and EC2 actually runs the website.
