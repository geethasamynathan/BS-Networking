Network Connectivity Tools in Ubuntu Linux

Network connectivity tools help administrators check whether systems can communicate, identify where communication fails, inspect DNS and routing, verify service ports, and collect evidence for troubleshooting.

Examples use Ubuntu Linux and Ubuntu on Windows Subsystem for Linux (WSL). Some operations require sudo; packet filtering and virtual networking may behave differently under WSL.

1. What are connectivity tools?

Connectivity tools are Linux commands and utilities that test communication between your computer, other computers, network devices, and internet services. Different tools check different layers: interface configuration, IP reachability, routing, name resolution, TCP/UDP ports, HTTP responses, or packet traffic.

Example: A browser cannot open https://example.com. One tool checks whether an IP address is configured; another tests DNS; another tests TCP port 443; and curl checks the HTTPS response. Together they isolate the fault.

2. Why are connectivity tools used?

  • Confirm the machine has an IP address and active network interface.
  • Test access to a gateway, server, website, or external network.
  • Diagnose DNS lookup, routing, firewall, and blocked-port issues.
  • Verify that a web server, API, SSH service, or database port is reachable.
  • Identify slow or failed connections and capture verifiable evidence.
  • Distinguish network problems from application or TLS problems.

Important: No one command proves that everything is healthy. A successful ping does not prove HTTPS works, and a failed ping does not prove a website is down.

4. Prepare Ubuntu for practice

Run the commands in an Ubuntu terminal. On WSL, open the Ubuntu application. Install only the tools that are missing.

Terminal — install utilities
sudo apt update
sudo apt install -y iputils-ping iproute2 dnsutils traceroute iputils-tracepath curl wget netcat-openbsd tcpdump openssl lsof

Optional utilities: sudo apt install -y network-manager (only when NetworkManager manages your environment) and sudo apt install -y ufw (for an Ubuntu installation that uses UFW).

WSL note: WSL networking is mediated by Windows. The default gateway may be virtual, nmcli may not manage the interface, and UFW rules may not behave like a dedicated Ubuntu server. Use read-only commands first. Do not change firewall/network settings on a remote or production system without authorization.

6. View network configuration: ip and hostname

ip is the standard Linux utility to inspect address assignment, link state, and routing. Run:

Commands
hostname -I
ip -br addr
ip -4 addr show
ip link show
ip route
Illustrative output — ip -br addr
lo        UNKNOWN    127.0.0.1/8
eth0      UP         172.22.97.32/20

lo is the loopback interface, while eth0 is a network interface. /20 is the network prefix length. UP signals an operational link, but does not by itself prove internet access.

Illustrative output — ip route
default via 172.22.96.1 dev eth0
172.22.96.0/20 dev eth0 proto kernel scope link src 172.22.97.32

Traffic outside the directly connected 172.22.96.0/20 network normally goes to the default gateway 172.22.96.1. Your addresses will differ.

7. Test reachability with ping

ping sends ICMP Echo Requests and measures replies. It helps test basic reachability, round-trip time, and packet loss.

Commands
ping -c 4 127.0.0.1
ping -c 4 1.1.1.1
ping -c 4 example.com
Illustrative output
64 bytes from 1.1.1.1: icmp_seq=1 ttl=56 time=18.5 ms
64 bytes from 1.1.1.1: icmp_seq=2 ttl=56 time=20.1 ms
...
4 packets transmitted, 4 received, 0% packet loss

Interpretation: -c 4 sends four requests; time is round-trip latency; 0% packet loss means all four replies arrived. Some hosts block ICMP, so interpret failure alongside TCP/HTTP tests.

8. Locate routing hops with tracepath and traceroute

These utilities help reveal the route taken toward a destination. Intermediate routers may filter responses, so asterisks do not necessarily indicate a fault.

Commands
tracepath example.com
traceroute example.com
traceroute -T -p 443 example.com

traceroute -T -p 443 sends TCP-based probes to destination port 443 and may be more informative when other probe types are filtered. It may require privileges in some environments.

9. Diagnose DNS with dig, host, and resolvectl

DNS converts a domain name into addresses and provides other records. A website may fail by hostname even while an IP-based network test succeeds.

Commands
dig example.com A

dig example.com AAAA

dig gmail.com MX

dig example.com NS

dig example.com TXT

dig +short example.com

host example.com
getent ahosts example.com
cat /etc/resolv.conf
resolvectl status

A is IPv4, AAAA is IPv6, MX is a mail exchanger, NS is a name server, and TXT contains text-based DNS metadata. resolvectl works when systemd-resolved is installed and active; it may not be usable in every WSL environment.

Illustrative output — dig +short example.com
93.184.215.14

Actual DNS addresses can change. Do not depend on an example output IP for future tests.

10. Test web services with curl and wget

These tools test application-layer access. A website may resolve and answer a ping but still have an HTTPS problem.

Commands
curl -I https://example.com
curl -v https://example.com -o /dev/null
curl -L https://example.com -o page.html
curl -sS -o /dev/null -w 'HTTP=%{http_code} DNS=%{time_namelookup}s Connect=%{time_connect}s Total=%{time_total}s\n' https://example.com
wget --spider https://example.com

-I requests response headers; -v shows connection/TLS details; -L follows redirects; -o sets an output file; -w displays timing metrics. wget --spider checks a URL without saving a normal download.

A 200 status usually means success; 301/302 means redirect; 403 means access is forbidden; 404 means the requested resource was not found; 500 is a server-side error. These are HTTP results, not general network diagnoses.

11. Inspect local ports using ss

A service must listen on the appropriate address and port to accept inbound connections.

Commands
ss -tuln
sudo ss -lntp
ss -tan
sudo lsof -iTCP:8080 -sTCP:LISTEN
Illustrative output
State  Recv-Q Send-Q Local Address:Port  Peer Address:Port
LISTEN 0      5      127.0.0.1:8080      0.0.0.0:*

-t means TCP, -u UDP, -l listening sockets, -n numeric addresses, and -p process names. A listener on 127.0.0.1 accepts local connections but is not directly exposed on other network interfaces.

12. Test TCP ports using nc (netcat)

nc helps verify whether a TCP connection can be established to a specific host and port.

Commands
nc -vz -w 3 example.com 443
nc -vz -w 3 127.0.0.1 8080

-v is verbose, -z performs a connect check without sending application data, and -w 3 sets a timeout. A successful TCP connect is not proof that the application protocol works correctly.

Only test ports on systems you own or are authorized to assess. Avoid broad network scans of third-party systems.

13. Examine routes and neighbor discovery

Commands
ip route
ip route get 1.1.1.1
ip neigh show

ip route get predicts the next hop, interface, and source address Linux would choose for a destination. ip neigh show shows neighbor mappings, commonly IPv4 ARP or IPv6 neighbor discovery entries. Neighbor entries may be empty until traffic has occurred.

14. View network management status

Commands
nmcli device status
networkctl status
cat /etc/resolv.conf

nmcli is useful when NetworkManager is running. networkctl reports status from systemd-networkd-related information. Neither service is guaranteed to manage networking inside WSL; use ip as the reliable baseline inspection tool.

15. Capture packets with tcpdump

Packet captures show whether traffic reaches an interface. They are useful when the application log is not enough to explain an issue.

Terminal A — capture ICMP
sudo tcpdump -ni any -c 10 icmp
Terminal B — generate traffic
ping -c 4 1.1.1.1

-n avoids DNS lookups, -i any captures on available interfaces, and -c 10 stops after ten packets. If no packets match, the capture can wait; stop it with Ctrl+C. Other useful filters include tcp port 8080 and udp port 53.

Privacy: Packet captures may contain IP addresses, service metadata, and sensitive payloads. Capture only authorized traffic, minimize scope, and restrict saved capture files.

16. Inspect TLS connections

For HTTPS, it is useful to distinguish TCP reachability from certificate or TLS errors.

Command
openssl s_client -connect example.com:443 -servername example.com

-connect selects the destination; -servername sends the TLS Server Name Indication (SNI), which is important on servers hosting multiple sites. Review certificate dates, the verification result, and handshake messages. Use Ctrl+C to exit if the session remains open.

17. Check firewall rules safely

Read-only checks
sudo ufw status verbose
sudo nft list ruleset
sudo iptables -S

These commands show different filtering interfaces where installed. UFW is not always enabled; modern Linux commonly uses nftables underneath. WSL traffic is also affected by Windows-side networking and firewall configuration.

Do not disable an entire firewall simply to troubleshoot; inspect logs and add narrowly scoped, authorized rules when needed.

18. Collect system and service log evidence

Logs connect the symptom to a timestamped error. Depending on the Ubuntu setup, journald and named services may be available.

Commands
journalctl -b -p warning --no-pager
journalctl --since '15 minutes ago' --no-pager
sudo journalctl -u ssh --since '30 minutes ago' --no-pager
dmesg | tail -n 30

-b limits to the current boot; -p warning selects warning-and-higher priority entries; -u ssh selects SSH service logs when that unit exists. Systemd journaling and dmesg permissions vary, especially on WSL.

19. Practical hands-on labs

Lab A — Identify the machine and verify DNS/HTTPS

  1. Inspect local IP addresses and routes.
  2. Test local loopback and a public IP.
  3. Resolve a hostname.
  4. Request the website headers.
  5. Record which layer fails, if any.
Lab A
hostname -I
ip -br addr
ip route
ping -c 3 127.0.0.1
ping -c 3 1.1.1.1
dig +short example.com
curl -I https://example.com

Diagnosis: A numeric IP test working while DNS fails points toward name resolution. DNS working while curl fails points toward the TCP/TLS/HTTP path.

Lab B — Start a real local web service

This lab avoids external dependencies. It works on typical Ubuntu/WSL installations with Python 3.

Terminal A — create and serve page
mkdir -p ~/connectivity-lab/site
cd ~/connectivity-lab/site
printf '%s\n' '<h1>Ubuntu Connectivity Lab</h1>' > index.html
python3 -m http.server 8080 --bind 127.0.0.1
Terminal B — inspect and test
ss -lntp | grep ':8080'
nc -vz 127.0.0.1 8080
curl http://127.0.0.1:8080/
curl -I http://127.0.0.1:8080/
Illustrative successful result
<h1>Ubuntu Connectivity Lab</h1>

Return to Terminal A and press Ctrl+C when finished. If port 8080 is already occupied, use port 8081 in both the server and test commands.

Lab C — Understand common connection failures

With the local server stopped
nc -vz -w 2 127.0.0.1 8080
curl --connect-timeout 2 http://127.0.0.1:8080/

Expected: With no listener, the local TCP connection generally fails with “Connection refused.” This differs from a timeout, which may indicate no response, filtering, or a network path issue.

Lab D — Verify a DNS mismatch

Compare DNS and web behavior
dig +short example.com
getent ahosts example.com
curl -I https://example.com
curl -I https://nonexistent.invalid

.invalid is reserved for invalid domain names, so the last command should fail DNS resolution. This is an intentional controlled failure.

Lab E — Build an evidence file

Run these read-only checks
mkdir -p ~/connectivity-lab/evidence
{
  date -Is
  echo '--- addresses ---'
  ip -br addr
  echo '--- routes ---'
  ip route
  echo '--- DNS ---'
  dig +short example.com
  echo '--- HTTPS ---'
  curl -sS -o /dev/null -w 'http=%{http_code} total=%{time_total}s\n' https://example.com
} 2>&1 | tee ~/connectivity-lab/evidence/network-check.txt
cat ~/connectivity-lab/evidence/network-check.txt

The saved report includes a timestamp and observations. It is useful for reproducing and documenting issues; it does not change network settings.

3. DNS & path

4. TCP & HTTP

5. Evidence
logs / tcpdump
SymptomFirst useful checksWhat to verify
“Could not resolve host”dig, getent ahostsDNS servers, search domains, response records
“Connection refused”ss -lntp, nc -vzIs the service listening on the correct port/interface?
Connection timeoutip route get, nc, firewall checksRoute, filtering, remote service, packet return path
HTTP 404curl -vCorrect URL, application route, reverse-proxy mapping
Certificate failurecurl -v, openssl s_clientCertificate chain, name, expiry, trusted CA
Intermittent slownessping, curl -w, logsLoss, DNS time, TCP time, server response time

Sample root-cause note

Issue: Local test site not reachable at 127.0.0.1:8080.
Evidence: curl returns connection refused; ss -lntp shows no listener on 8080.
Root cause: Test web server was stopped.
Fix: Restart the Python HTTP server.
Validation: ss shows a listener and curl returns HTTP 200.
Prevention: For a real managed application, use a service manager and service monitoring.

21. Quick command reference

Connectivity checks
ip -br addr                        # Addresses and link state
ip route                           # Routes / default gateway
ip route get 1.1.1.1               # Selected outgoing path
ping -c 4 1.1.1.1                 # Basic IP reachability
tracepath example.com              # Route hop discovery
dig example.com A                  # DNS IPv4 record
dig example.com AAAA               # DNS IPv6 record
curl -I https://example.com        # HTTP headers
curl -v https://example.com        # HTTP + TLS diagnostic
sudo ss -lntp                      # Listening TCP sockets and processes
nc -vz -w 3 example.com 443        # TCP port connectivity
sudo tcpdump -ni any -c 10 icmp    # ICMP packet capture
sudo ufw status verbose            # UFW status (if installed)
journalctl -b -p warning           # Current boot warnings
