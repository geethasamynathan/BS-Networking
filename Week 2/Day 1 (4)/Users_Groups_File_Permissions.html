Linux Users, Groups & File Permissions

A complete story-driven tutorial: create real users and groups, create a company directory structure, assign ownership, grant access, restrict access, test the results, learn ACLs and special permission bits, and clean up safely.

Goal: Understand each command, its output, and exactly who can do what on a file or directory.

LAB 01

Plan our company access

Story: You are the Linux Administrator for TechNova. HR has confidential salary files. Developers must work together on code. An auditor can inspect selected reports, but must not modify them. We will build the access model from scratch.

Step 1 — Check your administrator account

COMMAND 
whoami
id
sudo -v
EXAMPLE OUTPUT
geetha
uid=1000(geetha) gid=1000(geetha) groups=1000(geetha),27(sudo)

Explanation: Your output will differ. id shows your numeric user ID, primary group, and supplementary groups. sudo -v checks that you can perform administrative tasks.

Step 2 — Check whether test names already exist

COMMAND 
getent group labhr
getent passwd hruser
EXAMPLE OUTPUT
(no output if these names do not exist)

Explanation: Before creating anything, check for collisions. If the names already exist, choose a different lab prefix instead of changing an unrelated account.

Access policy: HR folder: only HR group. Development folder: development group can collaborate. Audit reports: auditor read-only. The public-drop folder demonstrates sticky-bit behavior. These are lab examples, not an exhaustive production security policy.
LAB 02

Understand users, groups and identity

Every Linux process runs with a user identity (UID) and group identities (GID). A file has an owning user, owning group and permission bits. Linux uses these to decide whether access is granted.

Step 1 — Inspect an existing user

COMMAND 
id
getent passwd "$(whoami)"
EXAMPLE OUTPUT
uid=1000(geetha) gid=1000(geetha) groups=1000(geetha),27(sudo)
geetha:x:1000:1000:...:/home/geetha:/bin/bash

Explanation: /etc/passwd stores account metadata, not password hashes. /etc/shadow stores password-related data; read access is restricted.

Step 2 — Understand a passwd record

COMMAND 
getent passwd root
EXAMPLE OUTPUT
root:x:0:0:root:/root:/bin/bash

Explanation: Fields: username, placeholder, UID, primary GID, description, home directory and login shell.

LAB 03

Create Linux groups

A group represents a team. Granting permissions to groups is easier and safer than managing each employee independently.

Step 1 — Create four groups

COMMAND 
sudo groupadd labhr
sudo groupadd labdev
sudo groupadd labaudit
sudo groupadd labshared
EXAMPLE OUTPUT
(no output on success)

Explanation: groupadd creates an entry in the system group database. No output usually means success.

Step 2 — Verify groups

COMMAND 
getent group labhr
getent group labdev
getent group labaudit
getent group labshared
EXAMPLE OUTPUT
labhr:x:1002:
labdev:x:1003:
labaudit:x:1004:
labshared:x:1005:

Explanation: GID numbers are examples and depend on your machine. Group members appear after the final colon; new groups have no members yet.

Syntax: sudo groupadd GROUPNAME. For a name that already exists, Linux normally reports a group-exists error.
LAB 04

Create Linux users

We need four employee accounts. We give each a home directory and the Bash shell so we can test access interactively.

Step 1 — Create user accounts

COMMAND 
sudo useradd -m -s /bin/bash hruser
sudo useradd -m -s /bin/bash developer1
sudo useradd -m -s /bin/bash developer2
sudo useradd -m -s /bin/bash auditor1
EXAMPLE OUTPUT
(no output on success)

Explanation: -m creates the home directory. -s specifies the login shell. These users initially have no login passwords set by these commands.

Step 2 — Verify account properties

COMMAND 
getent passwd hruser
getent passwd developer1
ls -ld /home/hruser /home/developer1
EXAMPLE OUTPUT
hruser:x:1001:1006::/home/hruser:/bin/bash
developer1:x:1002:1007::/home/developer1:/bin/bash
drwxr-x--- ... /home/hruser
drwxr-x--- ... /home/developer1

Explanation: Numeric IDs and home-directory permission modes vary by Ubuntu configuration. Use the real output to inspect the accounts.

Step 3 — Optional: set a password for interactive login

COMMAND 
sudo passwd hruser
EXAMPLE OUTPUT
New password:
Retype new password:
passwd: password updated successfully

Explanation: Typing the password will not display characters. sudo -u used later does not require these test-user passwords; setting passwords is optional for the lab.

LAB 05

Assign users to groups

Creating a group is not the same as placing a user in the group. Assign each employee to the appropriate team and verify membership.

Step 1 — Add users to supplementary groups

COMMAND 
sudo usermod -aG labhr,labshared hruser
sudo usermod -aG labdev,labshared developer1
sudo usermod -aG labdev,labshared developer2
sudo usermod -aG labaudit auditor1
EXAMPLE OUTPUT
(no output on success)

Explanation: -G supplies supplementary groups; -a appends without replacing existing supplementary memberships. Omitting -a can remove other supplementary groups.

Step 2 — Verify memberships

COMMAND 
id hruser
id developer1
id developer2
id auditor1
EXAMPLE OUTPUT
uid=1001(hruser) gid=1006(hruser) groups=1006(hruser),1002(labhr),1005(labshared)
...developer1 ... labdev ... labshared
...developer2 ... labdev ... labshared
...auditor1 ... labaudit

Explanation: The primary group is commonly a user-private group created automatically, while the team groups are supplementary. Exact IDs and ordering can differ.

Step 3 — Remove only one membership (example)

COMMAND 
sudo gpasswd -d developer2 labshared
id developer2
sudo usermod -aG labshared developer2
EXAMPLE OUTPUT
Removing user developer2 from group labshared
... (labshared absent in interim id output)

Explanation: This demonstrates revoking a single team membership. The final command restores developer2 for later labs. Existing login sessions may need re-login to refresh group membership.

Industry guidance: Prefer granting permission to job-role groups. Avoid adding ordinary employees to sudo just to share files.
LAB 06

Build a company folder structure

Now create three protected areas: confidential HR records, collaborative development work and auditor-readable reports. We also add a public-drop exercise folder.

Step 1 — Create the directory hierarchy

COMMAND 
sudo mkdir -p /srv/technova-lab/{hr,dev,audit,public-drop}
sudo ls -ld /srv/technova-lab/*
EXAMPLE OUTPUT
drwxr-xr-x ... /srv/technova-lab/audit
drwxr-xr-x ... /srv/technova-lab/dev
drwxr-xr-x ... /srv/technova-lab/hr
drwxr-xr-x ... /srv/technova-lab/public-drop

Explanation: mkdir -p creates parents as needed. Initial permission modes depend on the current umask and system settings.

Step 2 — Create illustrative files as root

COMMAND 
echo "EmployeeID,Name,Salary" | sudo tee /srv/technova-lab/hr/salaries.csv
echo "101,Anita,70000" | sudo tee -a /srv/technova-lab/hr/salaries.csv
echo "Release plan" | sudo tee /srv/technova-lab/dev/README.txt
echo "Quarterly status" | sudo tee /srv/technova-lab/audit/report.txt
EXAMPLE OUTPUT
EmployeeID,Name,Salary
101,Anita,70000
Release plan
Quarterly status

Explanation: tee writes files through sudo. Creating them as root is temporary: subsequent steps assign the correct owners and groups.

LAB 07

Understand rwx and octal permissions

ls -l displays the permission string. It has a file-type character, three triples for the owner/group/others, plus possible special markers.

Step 1 — Inspect file permissions

COMMAND 
ls -l /srv/technova-lab/dev/README.txt
stat -c "%A %a %U %G %n" /srv/technova-lab/dev/README.txt
EXAMPLE OUTPUT
-rw-r--r-- 1 root root ... README.txt
-rw-r--r-- 644 root root /srv/technova-lab/dev/README.txt

Explanation: stat prints both symbolic and numeric modes. Output shows a typical initial mode before we lock down access.

Step 2 — Demonstrate symbolic chmod on a throwaway file

COMMAND 
sudo touch /srv/technova-lab/dev/permissions-demo.txt
sudo chmod 640 /srv/technova-lab/dev/permissions-demo.txt
stat -c "%A %a %n" /srv/technova-lab/dev/permissions-demo.txt
EXAMPLE OUTPUT
-rw-r----- 640 /srv/technova-lab/dev/permissions-demo.txt

Explanation: Mode 640 means owner read/write (6), group read (4), others none (0). For a regular file, x grants execution permission; it does not make non-executable content valid program code.

Step 3 — Change permission symbolically

COMMAND 
sudo chmod g+w /srv/technova-lab/dev/permissions-demo.txt
sudo chmod o-rwx /srv/technova-lab/dev/permissions-demo.txt
stat -c "%A %a" /srv/technova-lab/dev/permissions-demo.txt
EXAMPLE OUTPUT
-rw-rw---- 660

Explanation: u = owning user, g = group, o = others, a = all. + adds, - removes, = sets precisely.

Octal math: read = 4, write = 2, execute = 1. Thus 7 = 4+2+1, 6 = 4+2, 5 = 4+1, 4 = read only, 0 = no rights. Common modes: files 600, 640, 644; directories 700, 750, 770, 755. Avoid granting execute on ordinary data files unless needed.
LAB 08

Ownership: chown and chgrp

The file owner and owning group are independent metadata attributes. Use chown to modify owner/group and chgrp to modify only the owning group.

Step 1 — Assign HR ownership and permissions

COMMAND 
sudo chown -R hruser:labhr /srv/technova-lab/hr
sudo chmod 2770 /srv/technova-lab/hr
sudo chmod 660 /srv/technova-lab/hr/salaries.csv
EXAMPLE OUTPUT
(no output on success)

Explanation: The HR folder is owned by hruser and labhr. 2770 sets setgid plus owner/group full access and no access for others. The file is read/write for owner and group.

Step 2 — Assign shared developer group

COMMAND 
sudo chown -R root:labdev /srv/technova-lab/dev
sudo chmod 2770 /srv/technova-lab/dev
sudo chmod 660 /srv/technova-lab/dev/README.txt
sudo chmod 660 /srv/technova-lab/dev/permissions-demo.txt
EXAMPLE OUTPUT
(no output on success)

Explanation: Developer team members access this directory through group membership. Setgid helps new entries inherit labdev as their group.

Step 3 — Assign audit file read permissions

COMMAND 
sudo chown -R root:labaudit /srv/technova-lab/audit
sudo chmod 2750 /srv/technova-lab/audit
sudo chmod 640 /srv/technova-lab/audit/report.txt
EXAMPLE OUTPUT
(no output on success)

Explanation: Auditors can traverse and list the audit directory and read report.txt; only root can modify the report and the audit directory.

Step 4 — Verify final owner/group and modes

COMMAND 
sudo stat -c "%A %a %U:%G %n" /srv/technova-lab/{hr,dev,audit}
sudo stat -c "%A %a %U:%G %n" /srv/technova-lab/{hr/salaries.csv,dev/README.txt,audit/report.txt}
EXAMPLE OUTPUT
drwxrws--- 2770 hruser:labhr /srv/technova-lab/hr
drwxrws--- 2770 root:labdev /srv/technova-lab/dev
drwxr-s--- 2750 root:labaudit /srv/technova-lab/audit
-rw-rw---- 660 hruser:labhr .../salaries.csv
-rw-rw---- 660 root:labdev .../README.txt
-rw-r----- 640 root:labaudit .../report.txt

Explanation: The lowercase s in the group execute position indicates setgid together with execute; it is normal for these shared directories.

LAB 09

Restrict HR access

Try to view salaries as authorized HR and unauthorized developer. This is the clearest way to understand restriction.

Step 1 — HR reads the protected file

COMMAND 
sudo -u hruser cat /srv/technova-lab/hr/salaries.csv
EXAMPLE OUTPUT
EmployeeID,Name,Salary
101,Anita,70000

Explanation: The effective process user is hruser, whose group membership includes labhr. The path can be traversed and the file can be read.

Step 2 — Developer attempts to read salaries

COMMAND 
sudo -u developer1 cat /srv/technova-lab/hr/salaries.csv
EXAMPLE OUTPUT
cat: /srv/technova-lab/hr/salaries.csv: Permission denied

Explanation: The developer is not in labhr and others have no rights to traverse the HR directory.

Step 3 — Auditor attempts to list HR files

COMMAND 
sudo -u auditor1 ls /srv/technova-lab/hr
EXAMPLE OUTPUT
ls: cannot open directory '/srv/technova-lab/hr': Permission denied

Explanation: The directory denies both search and listing to users outside the authorized owner/group classes.

Step 4 — Show file and directory details

COMMAND 
namei -l /srv/technova-lab/hr/salaries.csv
EXAMPLE OUTPUT
f: /srv/technova-lab/hr/salaries.csv
...
drwxrws--- hruser labhr hr
-rw-rw---- hruser labhr salaries.csv

Explanation: namei -l inspects every component in the path, helping identify where directory traversal is blocked.

Security nuance: With Unix discretionary permissions, the owner-class bits take precedence for the owning user; users do not get an automatic union of owner, group and other rights. Root and privileged processes may bypass normal DAC checks, so these restrictions protect ordinary accounts, not administrators.
LAB 10

Team collaboration with setgid

Two developers need to create and edit files in the same project folder. Group membership provides shared authorization, but inherited group and umask also matter.

Step 1 — Verify directory setgid

COMMAND 
stat -c "%A %a %U:%G" /srv/technova-lab/dev
EXAMPLE OUTPUT
drwxrws--- 2770 root:labdev

Explanation: Directory setgid makes newly created files/subdirectories inherit the directory group on typical Linux filesystems.

Step 2 — Developer1 creates a file

COMMAND 
sudo -u developer1 sh -c 'umask 0002; echo "Feature A" > /srv/technova-lab/dev/feature.txt'
ls -l /srv/technova-lab/dev/feature.txt
EXAMPLE OUTPUT
-rw-rw-r-- 1 developer1 labdev ... feature.txt

Explanation: The new file inherits group labdev; umask 0002 allows group write. Others may have read bits on the file, but the 2770 parent directory blocks their traversal.

Step 3 — Developer2 appends to the shared file

COMMAND 
sudo -u developer2 sh -c 'echo "Feature B" >> /srv/technova-lab/dev/feature.txt'
cat /srv/technova-lab/dev/feature.txt
EXAMPLE OUTPUT
Feature A
Feature B

Explanation: Developer2 belongs to labdev and the file has group write. Both users can collaborate.

Step 4 — Stop another user from changing the project

COMMAND 
sudo -u auditor1 sh -c 'echo "Unauthorized" >> /srv/technova-lab/dev/feature.txt'
EXAMPLE OUTPUT
sh: 1: cannot create /srv/technova-lab/dev/feature.txt: Permission denied

Explanation: The auditor is not part of labdev; directory traversal denies access.

Production advice: For consistent group collaboration, set a controlled umask for participating processes or use default ACLs (Lab 14). Setgid alone changes group ownership, not necessarily group-write permission.
LAB 11

Directory permissions explained

Directory r, w and x behave differently from regular-file permissions. This is a frequent source of confusion.

Step 1 — Create a safe throwaway directory

COMMAND 
sudo mkdir -p /srv/technova-lab/dir-demo
sudo chmod 755 /srv/technova-lab/dir-demo
sudo sh -c 'echo hello > /srv/technova-lab/dir-demo/demo.txt'
sudo chmod 644 /srv/technova-lab/dir-demo/demo.txt
EXAMPLE OUTPUT
(no output)

Explanation: Parent permissions allow others to list names and traverse the directory, while the file is readable.

Step 2 — Remove directory read but preserve traversal

COMMAND 
sudo chmod 711 /srv/technova-lab/dir-demo
sudo -u auditor1 ls /srv/technova-lab/dir-demo
sudo -u auditor1 cat /srv/technova-lab/dir-demo/demo.txt
EXAMPLE OUTPUT
ls: cannot open directory '/srv/technova-lab/dir-demo': Permission denied
hello

Explanation: Without directory r, the user cannot list names. With x, a known filename can still be accessed if the file permissions allow.

Step 3 — Remove other execute/search permission

COMMAND 
sudo chmod 710 /srv/technova-lab/dir-demo
sudo -u auditor1 cat /srv/technova-lab/dir-demo/demo.txt
EXAMPLE OUTPUT
cat: /srv/technova-lab/dir-demo/demo.txt: Permission denied

Explanation: Without x on the parent directory, the user cannot traverse to the file, even if the file itself has read permission.

Step 4 — Restore and remove the throwaway directory

COMMAND 
sudo chmod 755 /srv/technova-lab/dir-demo
sudo rm -r /srv/technova-lab/dir-demo
EXAMPLE OUTPUT
(no output)

Explanation: Only this temporary directory is removed. This preserves the main HR/dev/audit lab.

Important: Deleting a file is controlled primarily by write + execute permissions on its containing directory, not by the file’s own write bit. Sticky bit and filesystem attributes can impose additional restrictions.
LAB 12

Default permissions and umask

The umask reduces default permission bits when a new file or directory is created. Files typically start from 666 (no execute) and directories from 777, before applying the umask.

Step 1 — Check current umask

COMMAND 
umask
umask -S
EXAMPLE OUTPUT
0022
u=rwx,g=rx,o=rx

Explanation: Output varies. Symbolic umask rendering describes the permissions allowed for directories under the mask.

Step 2 — Experiment inside a subshell

COMMAND 
( umask 0077; touch /tmp/technova-umask-demo-$$; stat -c "%a %n" /tmp/technova-umask-demo-$$; rm /tmp/technova-umask-demo-$$ )
EXAMPLE OUTPUT
600 /tmp/technova-umask-demo-12345

Explanation: The subshell prevents changing the parent shell umask. With mask 0077, a newly created regular file typically receives owner-only read/write.

Step 3 — Inspect the developer file

COMMAND 
stat -c "%a %U:%G" /srv/technova-lab/dev/feature.txt
EXAMPLE OUTPUT
664 developer1:labdev

Explanation: It was created with umask 0002. The directory setgid caused group ownership to become labdev.

Formula: In practice, creation mode is a bitwise operation: requested mode & ~umask, possibly further affected by default ACLs. It is not ordinary decimal subtraction.
LAB 13

Special permissions: sticky, setgid, setuid

Special permission bits can change execution identity or directory behavior. We focus on two useful directory cases, plus a warning about setuid.

Step 1 — Prepare a sticky shared drop directory

COMMAND 
sudo chown root:labshared /srv/technova-lab/public-drop
sudo chmod 1777 /srv/technova-lab/public-drop
stat -c "%A %a" /srv/technova-lab/public-drop
EXAMPLE OUTPUT
drwxrwxrwt 1777

Explanation: 1 is the sticky bit. In this demonstration all users can create entries, but users generally cannot remove or rename files owned by others. The final t shows sticky with execute enabled.

Step 2 — Two users create their own files

COMMAND 
sudo -u hruser sh -c 'echo HR > /srv/technova-lab/public-drop/hr.txt'
sudo -u developer1 sh -c 'echo DEV > /srv/technova-lab/public-drop/dev.txt'
ls -l /srv/technova-lab/public-drop
EXAMPLE OUTPUT
-rw-r--r-- ... developer1 developer1 dev.txt
-rw-r--r-- ... hruser hruser hr.txt

Explanation: Files belong to their creators. Because the directory is shared and sticky, users can create files while ordinary users cannot delete each other’s files.

Step 3 — Try unauthorized deletion

COMMAND 
sudo -u developer1 rm /srv/technova-lab/public-drop/hr.txt
EXAMPLE OUTPUT
rm: cannot remove '/srv/technova-lab/public-drop/hr.txt': Operation not permitted

Explanation: Even though the directory has write permission for everyone, the sticky bit prevents ordinary developer1 from removing the HR-owned entry.

Step 4 — Show the special bits in octal

COMMAND 
stat -c "%a %A" /srv/technova-lab/dev
stat -c "%a %A" /srv/technova-lab/public-drop
EXAMPLE OUTPUT
2770 drwxrws---
1777 drwxrwxrwt

Explanation: The thousands digit represents special permission bits: setuid=4, setgid=2, sticky=1.

Security caution: Setuid on executables is a privileged mechanism and should not be introduced casually. We do not create setuid programs in this tutorial. A world-writable directory should normally use a sticky bit; for controlled team sharing, prefer group-based 2770 instead of 1777.
LAB 14

ACLs: access for one specific user

ACL (Access Control List) allows a specific user to receive rights without adding that user to the owning group. The auditor needs read-only access to a specific development report, but must not edit it.

Step 1 — Install ACL utilities

COMMAND 
sudo apt install -y acl
EXAMPLE OUTPUT
... Setting up acl ...

Explanation: The setfacl and getfacl utilities manage POSIX ACLs on supported filesystems.

Step 2 — Create a report to share with the auditor

COMMAND 
sudo sh -c 'echo "Release readiness: PASS" > /srv/technova-lab/dev/release-report.txt'
sudo chown root:labdev /srv/technova-lab/dev/release-report.txt
sudo chmod 640 /srv/technova-lab/dev/release-report.txt
EXAMPLE OUTPUT
(no output)

Explanation: The report begins with owner write, developer group read and no others access.

Step 3 — Grant path traversal and specific file read

COMMAND 
sudo setfacl -m u:auditor1:--x /srv/technova-lab/dev
sudo setfacl -m u:auditor1:r-- /srv/technova-lab/dev/release-report.txt
getfacl -p /srv/technova-lab/dev/release-report.txt
EXAMPLE OUTPUT
...
user::rw-
user:auditor1:r--
group::r--
mask::r--
other::---

Explanation: The directory ACL grants just search/traversal (not listing), and the file ACL grants read. ACL masks can limit the effective rights of named users and groups.

Step 4 — Test permitted read and denied modification

COMMAND 
sudo -u auditor1 cat /srv/technova-lab/dev/release-report.txt
sudo -u auditor1 sh -c 'echo CHANGED >> /srv/technova-lab/dev/release-report.txt'
EXAMPLE OUTPUT
Release readiness: PASS
sh: 1: cannot create /srv/technova-lab/dev/release-report.txt: Permission denied

Explanation: The auditor can read that known filename but cannot modify its contents. The auditor cannot list the entire development directory.

Step 5 — Remove the specific ACL exception

COMMAND 
sudo setfacl -x u:auditor1 /srv/technova-lab/dev/release-report.txt
sudo setfacl -x u:auditor1 /srv/technova-lab/dev
getfacl -p /srv/technova-lab/dev/release-report.txt
EXAMPLE OUTPUT
...
user::rw-
group::r--
other::---

Explanation: The user-specific ACL entries are removed. Other ACL metadata may remain depending on filesystem and previous settings.

Default ACLs: For ongoing group-collaboration, administrators may set default ACL entries on directories (for example setfacl -d -m g:labdev:rwx DIR). Default ACLs are inherited by newly created children, but their effective access is still constrained by creation modes and masks. Apply only after understanding the inheritance rules.

Explanation: HR user succeeds.

Step 2 — Check unauthorized developer read of HR

COMMAND

EXAMPLE OUTPUT
cat: ... Permission denied

Explanation: Developer has no traverse access to the HR directory.

Step 3 — Check developer collaboration

COMMAND 
sudo -u developer2 cat /srv/technova-lab/dev/feature.txt
EXAMPLE OUTPUT
Feature A
Feature B

Explanation: Developer2 is in labdev and group permissions permit reading.

Step 4 — Check authorized auditor report read

COMMAND 
sudo -u auditor1 cat /srv/technova-lab/audit/report.txt
EXAMPLE OUTPUT
Quarterly status

Explanation: Auditor belongs to labaudit, which has read access to report.txt.

Step 5 — Check denied auditor report write

EXAMPLE OUTPUT

COMMAND

Explanation: A directory requires write plus execute to create new entries. The audit directory mode 2750 denies group write.

Expected outcomes: successful commands normally exit with code 0; access failures exit nonzero. Check with echo $? immediately after a command if you want to inspect the exit status.
LAB 16

Troubleshooting and auditing

When permission checks fail, determine whether the problem involves identity, group membership, file mode, directory traversal, ACLs, filesystem type or privileged-process settings.

Step 1 — Inspect account membership

COMMAND 
id developer1
getent group labdev
EXAMPLE OUTPUT
uid=... groups=...,labdev,...
labdev:x:...:developer1,developer2

Explanation: If membership was recently changed, re-login or start a new session so long-running processes refresh their group list.

Step 2 — Inspect every path component

COMMAND 
namei -l /srv/technova-lab/dev/feature.txt
EXAMPLE OUTPUT
...
drwxrws--- root labdev dev
-rw-rw-r-- developer1 labdev feature.txt

Explanation: A file can be world-readable but inaccessible if an ancestor directory blocks traverse/search.

Step 3 — Inspect the exact metadata and ACL

COMMAND 
stat -c "%A %a %U:%G %n" /srv/technova-lab/dev/feature.txt
getfacl -p /srv/technova-lab/dev
EXAMPLE OUTPUT
-rw-rw-r-- 664 developer1:labdev ...
# file: /srv/technova-lab/dev
...

Explanation: The ACL mask may reduce named-user or group effective permissions. POSIX ACLs are not automatically summed with traditional permissions.

Step 4 — Check the Linux filesystem location

COMMAND 
df -T /srv/technova-lab
findmnt -T /srv/technova-lab
EXAMPLE OUTPUT
Filesystem Type ...
...

Explanation: On WSL, Linux-native ext4-based storage behaves more predictably for these exercises than Windows-mounted filesystems such as /mnt/c.

Do not debug by running chmod -R 777 / or enabling broad write access. Diagnose the specific directory or file and change only what is necessary.
LAB 17

Cleanup lab users and groups

After completing the labs, remove the created accounts, groups and files. These commands target only the lab names used here. Review them before executing.

Step 1 — Inspect what will be removed

COMMAND 
sudo ls -la /srv/technova-lab
getent passwd hruser developer1 developer2 auditor1
getent group labhr labdev labaudit labshared
EXAMPLE OUTPUT
... (lab resources appear)

Explanation: Review the objects first. If the lab names correspond to real accounts on your system, do not continue.

Step 2 — Remove lab folder only

COMMAND 
sudo rm -r /srv/technova-lab
EXAMPLE OUTPUT
(no output on success)

Explanation: This removes the example data under /srv/technova-lab. Never replace this path with a broad system path.
