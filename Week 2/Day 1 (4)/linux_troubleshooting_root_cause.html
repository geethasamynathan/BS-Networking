Part 2 – Resolving Connectivity Issues

4. Incident INC-101: Employee application cannot be reached

The API should respond at http://127.0.0.1:8090/health, but employees report a connection error. Build an actual local application to use in later labs.

5. Build the sample troubleshooting application

Step 1 – Create app:

nano "$LAB/app/server.py"

Paste:

from http.server import BaseHTTPRequestHandler, HTTPServer
from pathlib import Path
from datetime import datetime, timezone
import json
import os

BASE = Path(__file__).resolve().parent.parent
REPORT_DIR = Path(
    os.environ.get("REPORT_DIR", str(BASE / "reports"))
)

class Handler(BaseHTTPRequestHandler):

    def send_json(self, status, data):
        body = json.dumps(data).encode("utf-8")
        self.send_response(status)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def do_GET(self):
        if self.path == "/health":
            self.send_json(200, {
                "status": "healthy",
                "time": datetime.now(timezone.utc).isoformat()
            })

        elif self.path == "/report":
            try:
                REPORT_DIR.mkdir(parents=True, exist_ok=True)
                path = REPORT_DIR / "employees.txt"
                path.write_text("101,Geetha,Training\n102,Ravi,IT\n")
                self.send_json(200, {"result": "report saved"})
            except OSError as error:
                print(f"REPORT_ERROR: {error}", flush=True)
                self.send_json(500, {
                    "error": "Report could not be saved"
                })

        else:
            self.send_json(404, {"error": "not found"})

    def log_message(self, fmt, *args):
        print(
            f"{datetime.now(timezone.utc).isoformat()} "
            f"{self.client_address[0]} {fmt % args}",
            flush=True
        )

HTTPServer(("127.0.0.1", 8090), Handler).serve_forever()

Endpoints:

Endpoint Purpose
/health Returns application health
/report Creates employee report

6. Reproduce the connectivity failure

Stop application in terminal 1 with Ctrl+C. Diagnose in terminal 2:

curl -v --connect-timeout 3 http://127.0.0.1:8090/health

Expected: Failed to connect to 127.0.0.1 port 8090.

Diagnosis 1 – IP / loopback

ip -br addr
ip addr show lo

Diagnosis 2 – Port listener

ss -ltnp '( sport = :8090 )'

No output indicates no matching listener.

Diagnosis 3 – Process

pgrep -af 'python3 app/server.py'

Diagnosis 4 – TCP

nc -vz -w 3 127.0.0.1 8090

Expected: Connection refused.

7. Identify, fix and verify

Evidence Result Conclusion
ip addr Loopback available Local IP interface exists
ss No port 8090 listener No accepting application socket
pgrep No application process Application stopped
curl Connection refused HTTP request cannot connect

Restart in terminal 1:

cd "$LAB"
python3 app/server.py

Verify from terminal 2:

curl -i http://127.0.0.1:8090/health

Confirmed root cause: Application process stopped; no listener on port 8090.

Symptom Next investigation
Connection refused Listener, port, rejection
Connection timed out Routing, firewall, destination, loss
No route to host Routing and path
Name not resolved DNS / hosts
TCP succeeds, HTTP 500 Application
HTTP 502 Proxy/backend
TLS certificate error Certificate, name, trust

Part 3 – Resolving Service Issues

8. Incident INC-102: Employee API service fails to start

The application works manually but fails after deployment as a service.

<div class="diagram"><strong>Service lifecycle</strong><div class="horizontal"><div>systemd<br><small>Service manager</small></div><span>→</span><div>Python<br><small>Application process</small></div><span>→</span><div>8090<br><small>Listening port</small></div></div><p>If Python cannot execute or exits, systemd reports a failure and the port can become unavailable.</p></div>

9. Create the systemd service

Stop the manually running Python app first (Ctrl+C).

export LAB="$HOME/Linuxtraining/troubleshooting-lab"
LABUSER="$(id -un)"

sudo tee /etc/systemd/system/technova-api.service > /dev/null <<EOF
[Unit]
Description=TechNova Troubleshooting API
After=network.target

[Service]
Type=simple
User=$LABUSER
WorkingDirectory=$LAB
ExecStart=/usr/bin/python3 $LAB/app/server.py
Restart=no

[Install]
WantedBy=multi-user.target
EOF

Register/start:

sudo systemctl daemon-reload
sudo systemctl start technova-api
systemctl status technova-api --no-pager
curl http://127.0.0.1:8090/health

Expected: Active: active (running) and healthy HTTP response.

10. Intentionally break the service

Backup:

sudo cp /etc/systemd/system/technova-api.service \
  /etc/systemd/system/technova-api.service.bak

Introduce wrong Python path:

sudo sed -i \
  's#/usr/bin/python3#/usr/bin/python3-missing#' \
  /etc/systemd/system/technova-api.service

Restart and inspect:

sudo systemctl daemon-reload
sudo systemctl restart technova-api
systemctl status technova-api --no-pager
sudo journalctl -u technova-api -n 30 --no-pager
systemctl cat technova-api
ls -l /usr/bin/python3
ls -l /usr/bin/python3-missing

Expected: Active: failed, often status=203/EXEC, and messages such as Failed at step EXEC.

11. Restore and verify

sudo cp /etc/systemd/system/technova-api.service.bak \
  /etc/systemd/system/technova-api.service
sudo systemctl daemon-reload
sudo systemctl reset-failed technova-api
sudo systemctl restart technova-api
systemctl is-active technova-api
curl -i http://127.0.0.1:8090/health

Root cause: nonexistent executable in ExecStart. Prevent with configuration and executable-path validation.

sudo systemd-analyze verify /etc/systemd/system/technova-api.service
systemctl show technova-api -p ExecStart -p User -p WorkingDirectory
systemctl --failed

Part 4 – Resolving Permission Issues

12. Incident INC-103: Permission denied when saving a report

The API health endpoint works, but /report fails because its process cannot write to the report directory. A running process does not guarantee it can access every directory.

13. Understand Linux permissions

<div class="diagram"><strong>Permission model: -rwxr-xr-- (754)</strong><div class="horizontal"><div class="blue">Owner<br><big>rwx</big><br><small>Read, write, execute</small></div><div class="green">Group<br><big>r-x</big><br><small>Read and execute</small></div><div class="amber">Others<br><big>r--</big><br><small>Read only</small></div></div></div>

Permission File meaning Directory meaning
r (4) Read contents List entries
w (2) Modify contents Create/delete/rename entries (also needs x)
x (1) Execute Traverse directory

Examples: 644 = rw-r--r--, 640 = rw-r-----, 755 = rwxr-xr-x, 750 = rwxr-x---, 700 = rwx------.

14. Reproduce permission denied

systemctl is-active technova-api
curl -i http://127.0.0.1:8090/report
cat "$LAB/reports/employees.txt"

Now remove owner write permission:

chmod 555 "$LAB/reports"

Temporarily restore owner write, delete test report, then disable write again so the next request must create it:

chmod 755 "$LAB/reports"
rm -f "$LAB/reports/employees.txt"
chmod 555 "$LAB/reports"
curl -i http://127.0.0.1:8090/report

Expected: HTTP/1.0 500 Internal Server Error.

15. Collect permission evidence

ls -ld "$LAB/reports"
stat -c '%U %G %A %a %n' "$LAB/reports"
namei -l "$LAB/reports"
systemctl show technova-api -p User
sudo journalctl -u technova-api -n 30 --no-pager

Expected directory mode: dr-xr-xr-x, and a REPORT_ERROR with permission denied.

16. Apply the correct fix

chmod 755 "$LAB/reports"
curl -i http://127.0.0.1:8090/report
cat "$LAB/reports/employees.txt"

Expected: HTTP 200 and report content.

Industry investigations:

ls -ld /path/to/directory
id serviceuser
namei -l /path/to/directory
getfacl /path/to/directory

Install acl if getfacl is missing. Authorized production examples (placeholder users/groups):

sudo chown serviceuser:appgroup /path/to/directory
sudo chmod 750 /path/to/directory

Never use chmod 777 as a quick fix. Root cause: directory lacked write permission for the service account. Prevention: deployment ownership/permissions validation and least privilege.

Part 5 – Resolving Disk Issues

17. Incident INC-104: Payroll job fails with “No space left on device”

A payroll job cannot save files. Possibilities include disk blocks, inode exhaustion, quotas, mount restrictions and permissions.

<div class="diagram"><strong>Disk diagnostic decision tree</strong><div class="steps"><div>File write fails</div><div>Check blocks: df -h</div><div>Check inodes: df -i</div><div>Check mounts, quotas, permissions, read-only state</div><div>Locate usage: du / find / lsof</div><div>Apply safe corrective action</div><div>Retest and review logs</div></div></div>

18. Essential disk investigation commands

df -h
df -i
findmnt
lsblk -f
du -sh "$LAB"/*
find "$LAB" -type f -size +10M -ls
du -h --max-depth=1 "$LAB" | sort -hr
sudo journalctl -k -p warning -n 50

19. Safe disk-full simulation

Important: Do not fill the root disk. Instead, simulate a file-size-limit failure (not a full filesystem). It typically yields “File size limit exceeded” or “File too large,” rather than ENOSPC.

Create script:

nano "$LAB/scripts/disk-write-test.sh"

#!/bin/bash
cd "$HOME/Linuxtraining/troubleshooting-lab" || exit 1
ulimit -f 1024
echo "Starting file-write test"
dd if=/dev/zero of=data/large-test.bin \
   bs=1024 count=4096 status=progress
echo "Write command exit status: $?"

Run and inspect:

chmod +x "$LAB/scripts/disk-write-test.sh"
bash "$LAB/scripts/disk-write-test.sh"
ls -lh "$LAB/data/large-test.bin"
df -h "$LAB/data"
ulimit -f
rm -f "$LAB/data/large-test.bin"

This confirms a per-process file-size limit, not necessarily a full disk. Root cause must match the observed error.

20. Other disk failure cases

A – Blocks exhausted

df -h /var
sudo du -xhd1 /var | sort -hr

B – Inodes exhausted

df -i

Free bytes can coexist with no free inodes.

C – Deleted file still occupies space

sudo lsof +L1

A running process may still hold the deleted file open. Restart only after evaluating impact.

D – Read-only filesystem

findmnt -no SOURCE,TARGET,FSTYPE,OPTIONS /

Investigate unexpected read-only state and kernel errors rather than blindly remounting. For the exercise, root cause is imposed file-size limit; real disk RCA requires filesystem and file-growth evidence.

21. Incident INC-105: Application becomes slow

The infrastructure team suspects CPU consumption. Reproduce with a controlled workload.

22. Understand the process lifecycle

State Meaning

23. Create a CPU-intensive process

yes > /dev/null &
CPU_PID=$!
echo "$CPU_PID"
ps -p "$CPU_PID" -o pid,ppid,stat,%cpu,%mem,etime,cmd
top -p "$CPU_PID"

Press q to exit top.

ps aux --sort=-%cpu | head -n 10
pstree -p "$CPU_PID"
kill "$CPU_PID"
ps -p "$CPU_PID"
wait "$CPU_PID" 2>/dev/null

A short-lived zombie entry is possible until reaped.

24. Simulate a background worker

nano "$LAB/scripts/background-worker.sh"

#!/bin/bash
while true
do
    echo "$(date -Is) Worker heartbeat"
    sleep 5
done

Run and monitor:

chmod +x "$LAB/scripts/background-worker.sh"
nohup "$LAB/scripts/background-worker.sh" \
  > "$LAB/logs/worker.log" 2>&1 &
WORKER_PID=$!
echo "$WORKER_PID"
tail -f "$LAB/logs/worker.log"

Press Ctrl+C to exit tail. Then:

ps -p "$WORKER_PID" -o pid,stat,etime,cmd
kill "$WORKER_PID"
pgrep -af python3
pstree -ap

Additional diagnostics (replace PID with actual PID):

sudo lsof -p PID
cat /proc/PID/limits
cat /proc/PID/status
ps aux --sort=-%mem | head -n 10
sudo journalctl -k | grep -Ei 'out of memory|oom|killed process'

Root cause in controlled CPU lab: yes produced continuous output redirected to /dev/null. In production, correlate CPU with request volume, expected load, changes and latency before concluding a fault.

Part 7 – Resolving DNS Issues

25. Incident INC-106: Employee API hostname cannot be resolved

Application works by IP, but employeeapp.lab.test fails.

<div class="diagram"><strong>Name resolution flow</strong><div class="horizontal"><div>Client<br><small>curl hostname</small></div><span>→</span><div>Resolver<br><small>Hosts / DNS</small></div><span>→</span><div>127.0.0.1<br><small>IP address</small></div><span>→</span><div>Employee API<br><small>8090</small></div></div></div>

26. Reproduce a DNS failure

sudo systemctl start technova-api
curl -i http://127.0.0.1:8090/health
curl --noproxy '*' -v \
  http://employeeapp.lab.test:8090/health
getent ahostsv4 employeeapp.lab.test
dig employeeapp.lab.test
cat /etc/hosts
cat /etc/resolv.conf
resolvectl status

If no DNS or local hosts record exists, name resolution fails. dig may show NXDOMAIN. Do not overwrite managed /etc/resolv.conf blindly.

27. Fix name resolution using a local hosts entry

sudo cp /etc/hosts /etc/hosts.technova.bak
echo "127.0.0.1 employeeapp.lab.test" | \
sudo tee -a /etc/hosts
getent ahostsv4 employeeapp.lab.test
curl --noproxy '*' -i \
  http://employeeapp.lab.test:8090/health

Expected: getent resolves 127.0.0.1, curl returns HTTP 200.

Important difference: getent uses system name-service sources including /etc/hosts; dig normally queries DNS directly. Thus getent may succeed while dig still finds no DNS record.

Clean up only the line created:

sudo sed -i \
  '/^127\.0\.0\.1 employeeapp\.lab\.test$/d' \
  /etc/hosts
grep employeeapp.lab.test /etc/hosts

28. DNS problem reference

Symptom Diagnostic command Possible cause
Hostname not resolving getent hosts HOST Invalid / absent name
DNS query fails dig HOST DNS service / record
DNS server unreachable dig @DNS_SERVER HOST Resolver connectivity
Wrong IP dig +short HOST Incorrect / outdated record
Resolver issue resolvectl status Resolver configuration
Different tool results getent vs dig NSS / hosts / DNS
DNS succeeds, application fails curl -v URL TCP, service, HTTP, TLS

Use approved company DNS configuration, rather than arbitrary public resolvers.

Part 8 – Root Cause Analysis and Documentation

29. What is Root Cause Analysis (RCA)?

RCA determines the underlying reason for an incident, beyond the symptom. It should explain: What happened? When? What was affected? What evidence was collected? What caused it? How was it resolved? How will recurrence be prevented?

30. Understand the Five Whys technique

Why Question Answer
1 Why can't employees access API? The service is not running.
2 Why isn't it running? The process failed to start.
3 Why did it fail? systemd could not execute the command.
4 Why couldn't it execute? ExecStart points to a nonexistent executable.
5 Why was it deployed? The lab deployment lacked path validation.

Technical root cause: Invalid executable path. Process improvement: Validate unit files and executable paths pre-deployment. Confirm Whys with real evidence.

33. Create an evidence collection script

nano "$LAB/scripts/incident-evidence.sh"

#!/bin/bash
set -u
LAB="$HOME/Linuxtraining/troubleshooting-lab"
OUT="$LAB/evidence"
STAMP=$(date +%Y%m%d_%H%M%S)
REPORT="$OUT/diagnosis_$STAMP.txt"
mkdir -p "$OUT"
{
  echo "TechNova Incident Evidence"
  echo "=========================="
  date -Is
  hostname
  echo; echo "=== IP ADDRESSES ==="
  ip -br addr
  echo; echo "=== ROUTES ==="
  ip route
  echo; echo "=== DNS ==="
  getent ahostsv4 example.com || true
  echo; echo "=== FILESYSTEM ==="
  df -h
  df -i
  echo; echo "=== MEMORY ==="
  free -h
  echo; echo "=== CPU / PROCESSES ==="
  ps aux --sort=-%cpu | head -n 10
  echo; echo "=== TCP LISTENERS ==="
  ss -ltn
  echo; echo "=== APPLICATION SERVICE ==="
  systemctl status technova-api --no-pager || true
  echo; echo "=== HTTP HEALTH ==="
  curl --noproxy '*' -sS \
    --connect-timeout 3 \
    -o /dev/null \
    -w 'HTTP_CODE=%{http_code}\n' \
    http://127.0.0.1:8090/health || true
  echo; echo "=== PERMISSIONS ==="
  stat -c '%U:%G %A %a %n' "$LAB/reports"
  echo; echo "=== RECENT SERVICE LOGS ==="
  journalctl -u technova-api -n 30 --no-pager || true
} > "$REPORT" 2>&1

echo "Evidence saved: $REPORT"

Execute:

chmod +x "$LAB/scripts/incident-evidence.sh"
"$LAB/scripts/incident-evidence.sh"
ls -lt "$LAB/evidence"
less "$(ls -t "$LAB"/evidence/diagnosis_*.txt | head -n 1)"

Run it while healthy, stop the service, run it again, restart, and run a third time:

sudo systemctl stop technova-api
"$LAB/scripts/incident-evidence.sh"
sudo systemctl start technova-api
"$LAB/scripts/incident-evidence.sh"

Compare selected generated reports (replace placeholders):

diff -u evidence/diagnosis_FILE1.txt evidence/diagnosis_FILE2.txt

Differences in timestamps and dynamic process details are expected. Redact secrets and sensitive information before sharing production evidence.

38. Key concepts to remember

A service can be active yet fail to write files. A host can answer ping while HTTP fails. DNS can resolve a name while a port remains closed. A write failure can involve permissions, quota, full filesystem, inode shortage, read-only mount, or a per-process file limit.

Observe → collect evidence → isolate failed layer → diagnose cause → apply smallest safe fix → verify → document.
