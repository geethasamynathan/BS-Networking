01. DevOps foundations

DevOps combines development and operations practices to deliver software reliably through collaboration, automation and feedback. Before automation, developers handed files to testers, who handed approved files to administrators for manual FTP/SFTP or server deployment.

Developer→Manual testing→Manual deployment→Server

Manual handovers cause delays, inconsistent environments, incorrect versions and difficult rollback. DevOps automates repeatable work while retaining appropriate approvals.

Plan→Code→Build→Test→Release→Deploy→Monitor→Feedback

CI/CDJenkins, GitHub Actions, Azure Pipelines

02. CI/CD principles

Continuous Integration (CI)

Frequently integrate changes into a shared repository and automatically validate them. A failed check prevents the dependent deployment.

Push / PR→Checkout→Validate→Package→Pass or fail

Continuous Delivery

Every passing change is prepared for release; production deployment can be approved manually.

CI→Artifact→Approval→Production

Continuous Deployment

Every qualifying change automatically reaches production after required checks pass.

CI→Artifact→Automatic deployment→Live site
ConceptOutputProduction approval
CIValidated changes / optional artifactNot applicable
Continuous deliveryRelease-ready artifactTypically manual
Continuous deploymentLive releaseAutomatic

03. GitHub Actions and Azure DevOps

GitHub Actions

Workflow automation built into GitHub. A repository event triggers jobs on runners. Earlier approaches included scripts, FTP, Jenkins, Travis CI, CircleCI and TeamCity; many remain in use.

GitHub event→Workflow→Runner→Jobs / steps→Deployment

Azure DevOps

Microsoft’s application lifecycle platform integrates planning, repositories, CI/CD, testing and package management. Microsoft’s tooling evolved from Visual SourceSafe and Team Foundation Server to Visual Studio Online, Visual Studio Team Services (VSTS), and Azure DevOps (2018). TFS evolved into Azure DevOps Server.

04. YAML from scratch

YAML Ain’t Markup Language is a human-readable data serialization format. Pipeline as Code means storing automation instructions in version control. YAML describes the instructions; the pipeline engine executes them.

# comment
application:
  name: ITTechGenie
  version: "1.0"
  enabled: true
  port: 8080
  technologies:
    - HTML
    - CSS
    - JavaScript
  server:
    host: localhost
SyntaxMeaning
key: valueMapping
- itemSequence item
#Comment
SpacesNesting (not tabs)
|Preserve multiline line breaks
>Fold consecutive text lines
[]Inline list
---Document start
steps:
  - name: Print messages
    run: |
      echo "Starting build"
      echo "Build completed"

Use consistent indentation (two spaces is customary). GitHub and Azure use the same YAML format but different schemas.

# GitHub Actions
name: Hello
on:
  push:
    branches: [main]
jobs:
  hello:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Hello"
# Azure Pipelines
trigger:
  - main
pool:
  vmImage: ubuntu-latest
steps:
  - script: echo "Hello"
    displayName: Print message

07. GitHub Actions: first workflow

A workflow contains jobs; jobs run on runners and contain steps. An action is a reusable step. An artifact is a generated output.

  1. Create .github/workflows/hello.yml locally.
  2. Add the following YAML, commit and push.
  3. Open GitHub → Actions → My First Workflow → latest run → hello-job → Print welcome message.
name: My First Workflow
on:
  push:
    branches: [main]
jobs:
  hello-job:
    runs-on: ubuntu-latest
    steps:
      - name: Print welcome message
        run: echo "Welcome to GitHub Actions"
git add .
git commit -m "Create first workflow"
git push

Expected: green status and the welcome message in logs. This demonstrates automation, not deployment. Remove hello.yml when the introductory exercise is complete.

08. GitHub Actions: CI/CD to GitHub Pages

GitHub Pages hosts static files. In your public sample repository choose Settings → Pages → Build and deployment → Source → GitHub Actions.

Push to main→Build / validate→dist artifact→Deploy job→GitHub Pages
  1. Create .github/workflows/deploy.yml using the following code.
  2. Commit and push.
  3. Open Actions → ITTechGenie Website CI-CD → latest run. Inspect build and deploy jobs.
  4. Open Settings → Pages and visit the published URL (typically https://YOUR-USERNAME.github.io/ittechgenie-web/).
name: ITTechGenie Website CI-CD
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch:
permissions:
  contents: read
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - name: Validate files
        run: |
          set -e
          test -s index.html
          test -s style.css
          test -s script.js
      - name: Validate JavaScript
        run: node --check script.js
      - name: Package website
        run: |
          mkdir -p dist
          cp index.html style.css script.js dist/
      - uses: actions/configure-pages@v5
        if: github.event_name != 'pull_request'
      - uses: actions/upload-pages-artifact@v4
        if: github.event_name != 'pull_request'
        with:
          path: dist
  deploy:
    needs: build
    if: github.ref == 'refs/heads/main' && github.event_name != 'pull_request'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pages: write
      id-token: write
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - name: Deploy website
        id: deployment
        uses: actions/deploy-pages@v4
KeywordMeaning
onEvent triggers
runs-onRunner image
usesReusable action
runShell command
withAction inputs
needsWait for successful dependency
ifConditional execution
permissionsWorkflow token permissions
environmentDeployment destination
workflow_dispatchManual run

Plain HTML does not need compilation. Build means validating and copying files into dist. Pull requests validate only; main pushes deploy. These checks do not prove browser functionality.

11. Create Azure Static Web Apps hosting

Azure Static Web Apps is a managed hosting service for static frontends. We choose it instead of provisioning a VM or web server.

  1. Open Azure Portal → Resource groups → Create RG-DevOps-Lab in an allowed region.
  2. Search Static Web Apps → Create. Select the training subscription, resource group, name ittechgenie-web-swa (use a unique suffix if required), Free plan if available, supported region.
  3. Choose deployment source Other and deployment token authorization if displayed. Review + create → Create → Go to resource.
  4. Overview → Manage deployment token → copy token privately. This is the Static Web App deployment token, NOT a GitHub PAT or Azure DevOps PAT.
Never paste tokens into YAML, screenshots, logs or GitHub. Reset exposed deployment tokens and update the secret.
Azure Pipelines→Secret deployment token→Azure Static Web Apps

12. Configure secret and complete Azure CI/CD

Step 1 — Configure the secret before saving deployment YAML

  1. Azure DevOps → Pipelines → select existing pipeline → Edit → Variables → New variable.
  2. Name: SWA_DEPLOYMENT_TOKEN. Value: paste the Static Web Apps deployment token. Select Keep this value secret. Leave user override unchecked.
  3. Confirm the variable and return to the YAML editor.

Step 2 — Replace existing azure-pipelines.yml

trigger:
  branches:
    include: [main]
pr:
  branches:
    include: [main]
pool:
  vmImage: ubuntu-latest
stages:
  - stage: CI
    displayName: Continuous Integration
    jobs:
      - job: Build
        steps:
          - checkout: self
          - script: |
              set -e
              test -s index.html
              test -s style.css
              test -s script.js
            displayName: Validate application files
          - script: node --check script.js
            displayName: Validate JavaScript syntax
          - script: |
              set -e
              mkdir -p "$(Build.ArtifactStagingDirectory)/website"
              cp index.html style.css script.js "$(Build.ArtifactStagingDirectory)/website/"
            displayName: Prepare deployment files
          - task: PublishPipelineArtifact@1
            inputs:
              targetPath: '$(Build.ArtifactStagingDirectory)/website'
              artifact: website
              publishLocation: pipeline
  - stage: CD
    displayName: Continuous Deployment
    dependsOn: CI
    condition: |
      and(succeeded(),
          eq(variables['Build.SourceBranch'], 'refs/heads/main'),
          ne(variables['Build.Reason'], 'PullRequest'))
    jobs:
      - job: Deploy
        steps:
          - checkout: none
          - download: current
            artifact: website
          - task: AzureStaticWebApp@0
            displayName: Deploy website to Azure
            inputs:
              cwd: '$(Pipeline.Workspace)/website'
              app_location: '/'
              api_location: ''
              output_location: ''
              skip_app_build: true
              skip_api_build: true
              azure_static_web_apps_api_token: $(SWA_DEPLOYMENT_TOKEN)

Step 3 — Validate and save

  1. Select Validate and save (or Save, depending on editor version). Resolve any YAML errors.
  2. In the Save dialog enter a commit message, e.g. Implement Azure website CI CD. For this lab choose Commit directly to main. Confirm Save.
  3. The main-branch commit may automatically queue the pipeline. Check Runs before starting a duplicate run.

Step 4 — Run manually if needed

14. Continuous delivery, approvals and rollback

Manual production approval (optional extension)

  1. Azure DevOps → Pipelines → Environments → New environment → Production (resource None).
  2. Production → Approvals and checks → Add check → Approvals. Select an authorized approver and configure timeout.
  3. Replace the CD jobs section with the deployment job below. Retain the existing CD stage condition and dependency.
  4. Save, run, and authorize the environment if required. Observe CI success followed by approval waiting. Approve to deploy.
jobs:
  - deployment: Deploy
    environment: Production
    strategy:
      runOnce:
        deploy:
          steps:
            - checkout: none
            - download: none
            - download: current
              artifact: website
            - task: AzureStaticWebApp@0
              inputs:
                cwd: '$(Pipeline.Workspace)/website'
                app_location: '/'
                api_location: ''
                output_location: ''
                skip_app_build: true
                skip_api_build: true
                azure_static_web_apps_api_token: $(SWA_DEPLOYMENT_TOKEN)

Rollback

Find the problematic commit and revert it without rewriting shared history. Review conflicts or subsequent changes before pushing. Required approvals still apply.

git log --oneline
git revert ACTUAL_COMMIT_SHA
git push origin main
Version 2 working→Version 3 issue→Revert commit→Working content restored

16. Classroom recap and assessment

Suggested delivery: foundations and YAML (60 min), website and Git (30 min), GitHub Actions (75 min), Azure DevOps and deployment (90 min), approvals and rollback (45 min), assessment (30 min). Approximately 5.5 hours; provisioning delays may vary.

What does YAML do?

Describes configuration; the pipeline engine executes it.

What is a runner or agent?

A machine executing pipeline jobs.

What is an artifact?

A generated output passed to deployment or retained for download.

Why checkout?

To fetch repository files into the job environment.

Why use a secret variable?

To avoid exposing deployment credentials in source code.

What happens when CI fails?

Dependent CD normally skips.

Can Azure Pipelines use GitHub?

Yes; Azure Repos is optional.

What goes in the Run pipeline Commit field?

An actual commit ID if a specific version is needed; otherwise leave blank.

What does skip_app_build do?

Tells the deployment task to use already prepared frontend files.

Does node --check test the button?

No; it checks JavaScript syntax. Browser testing is separate.
